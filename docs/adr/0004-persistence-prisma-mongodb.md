# 0004 — Persistence: MongoDB with Prisma 6.19

**Status:** Accepted (2026-09-21)

## Context

The challenge requires MongoDB. An order is a single aggregate (customer, line items, assigned employee,
history), and every state transition must be atomic and race-safe. We want a typed data layer and a
test setup that runs against real MongoDB semantics, not mocks.

The plan (decision 4) called for a time-boxed spike: use Prisma 8 if its MongoDB support is usable,
otherwise pin 6.19. Prisma 7 dropped MongoDB.

## Spike result

- `prisma@latest` is `8.0.0-rc.15`. It is still a release candidate, and the architecture is new: the CLI is built on
  `@prisma/orm-toolchain` / `@prisma/orm-framework`, and no `@prisma/client@8` is published (`@prisma/client@latest` is 7.10.0).
- Adopting it would mean building a graded submission on a pre-release runtime whose API and docs are still
  moving. That risk is not worth it for a 5-model schema.

## Decision

- **Prisma 6.19.3**, pinned exactly (`prisma` + `@prisma/client`), with the classic `prisma-client-js` generator.
  The client is generated by the api workspace's `postinstall`.
- **One document per order.** `customer`, `lineItems`, `assignedEmployee` (a `{ id, name }` snapshot), and later
  `history` are embedded composite types, so a transition is a single-document conditional update, with no multi-document transaction.
- **`PrismaService`** extends `PrismaClient` and is a global singleton (`PrismaModule`). It takes its URL from the
  injected `APP_CONFIG` (never `process.env`) and disconnects in `onModuleDestroy`.
- **Lazy connection.** It does not `$connect()` in `onModuleInit`. The API boots and serves `health { db: DOWN }` while MongoDB is
  unreachable, instead of crash-looping, and a Cloud Run cold start doesn't wait on the database. Prisma connects on
  the first query and reconnects after an outage. The health ping has a 2s timeout.
- **Replica set everywhere** (Prisma requires one on MongoDB):
  - local: `docker-compose.yml` runs a single-node `rs0`. Its healthcheck calls `rs.initiate` on first start and reports healthy
    once the node is primary. Clients use `directConnection=true`.
  - tests: `mongodb-memory-server` starts one `MongoMemoryReplSet` per run (Vitest `globalSetup`). Each worker gets its
    own database, and every collection is emptied (indexes kept) before each test.
  - production: Atlas, which is always a replica set.
- **MongoDB versions.** Tests run 8.0 (what Atlas M0 runs). The compose image is `mongo:8.2`, because 8.0.x
  exits at startup on Linux kernels ≥ 6.19 ([SERVER-121912](https://jira.mongodb.org/browse/SERVER-121912)),
  which current Docker Desktop VMs ship. We use only basic CRUD and conditional updates, which behave the same on both.

## Alternatives

- **Prisma 8 RC:** see the spike. It's worth revisiting once it is GA.
- **Mongoose:** more idiomatic for MongoDB (middleware, discriminators) and has no replica-set requirement, but its model
  typing is weaker and looser than a generated client.
- **Native `mongodb` driver:** the least magic and full control, but we would hand-write the typing and mapping.
  It is the fallback if Prisma's Mongo connector ever blocks us, and the repository interface (T5) keeps that swap local.
- **Eager `$connect()` in `onModuleInit`:** fails fast on a bad URL, but turns a database outage into an API
  crash loop and adds DB latency to every cold start. We already fail fast on a malformed URL through config validation.

## Consequences

- There are no MongoDB migrations. Indexes are declared in `schema.prisma` and applied with `yarn workspace @app/api db:push`.
- Prisma 6 is in maintenance mode. We'll plan the upgrade to Prisma 8 once it is GA.
- The first integration-test run downloads a mongod binary (~100 MB). CI caches it.
